1Overview: how the pieces fit

The website is a set of plain web pages (HTML, CSS and JavaScript files). There is no web server of our own to look after. Five outside services each do one job:

DreamHost

Where the domain name newberngrand.com is registered and where its DNS lives. DNS is the address book that tells the internet where the website is and where email goes.

GitHub

Holds every file of the website, with the full history of every change, in the repository newberngrand/Marina1. GitHub Pages hosts the site for free, straight from that repository.

Supabase

The database and back office: member logins, events and votes, documents and photos (file storage), the activity log, and small server programs (Edge Functions) that send email.

Resend

Sends the website’s email: announcements, vote receipts, password resets, help-request notices and review invitations, from an @newberngrand.com address.

Claude / Claude Code

The development tool. You describe a change in plain words; Claude edits the files, tests them on your computer, updates the database when needed and publishes to GitHub when you approve.

Google Workspace

The regular staff mailboxes (for example newberngrand@…). Not part of the website itself, but its DNS records sit beside the website’s at DreamHost, so they must be left alone when DNS is changed.

What happens when someone visits

  1. Their browser asks DNS (at DreamHost) where newberngrand.com is. DNS answers with GitHub’s addresses.
  2. GitHub Pages sends the pages, pictures and scripts from the repository.
  3. When a member logs in, votes or opens a document, the page talks directly to Supabase. Database rules decide what each person may see or change.
  4. When the site needs to send email, a Supabase Edge Function hands it to Resend, which delivers it.

What happens when we make a change

  1. Claude edits the files in the project folder on your computer and checks them in a local preview.
  2. Database changes are tested first in a trial run that is undone, then applied to Supabase only after you say “make it live”.
  3. The files are committed and pushed to GitHub. About a minute later GitHub Pages has rebuilt the site and the change is live. Open pages notice the new version and reload themselves.

3Find and install Claude

Claude is made by Anthropic. We use it in two forms that work the same way; most people only need the first.

Option A: the Claude desktop app (recommended)

  1. Go to claude.ai/download and download the Claude app for Windows (or Mac).
  2. Install it and sign in with your Claude account.
  3. Open the Code tab. Choose the project folder (see step 5 for getting the files), for example Documents\Marina1.
  4. Type what you want changed. Claude reads the files, explains what it will do, edits, previews the pages in its built-in browser and asks before anything goes live.

Option B: Claude Code in a terminal

  1. Follow the install steps at claude.com/claude-code (Anthropic’s official page). On Windows this is a one-line install in PowerShell.
  2. Open PowerShell in the project folder and type claude. Sign in when asked.

Connect Claude to the other services

  • GitHub: Claude uses the Git and GitHub command-line tools on your computer (step 4), signed in as you.
  • Supabase: in Claude, open Settings → Connectors, add the Supabase connector and authorize it with your Supabase account. Claude can then read the database, test changes and, with your OK, apply migrations and deploy Edge Functions.
  • Project settings: the folder .claude in the project holds launch.json, which tells Claude how to start the local preview (a small Python web server on port 8765). It stays on your computer and is never published.

How to work with Claude: say what you want in everyday words (“add a Help Desk button to the email”). Claude will ask before anything that affects the live site, the database or email. Saying “make it live” is the go-ahead to publish.

5Connect to GitHub (code and hosting)

Sign in and get the files

  1. In PowerShell: gh auth login → choose GitHub.com, HTTPS, and sign in with the browser. Say yes to using it for Git.
  2. Tell Git who you are (shown on each change):
    git config --global user.name "Your Name"
    git config --global user.email "you@example.com"
  3. Go to your Documents folder and copy the website down:
    cd $HOME\Documents
    gh repo clone newberngrand/Marina1
  4. Open that Marina1 folder in Claude’s Code tab.

How the repository is set up

  • Repository: github.com/newberngrand/Marina1 (public). Main branch: master.
  • Pages: Settings → Pages → Deploy from a branch, branch master, folder / (root).
  • Custom domain: newberngrand.com, with Enforce HTTPS on. The file CNAME in the repository holds the domain name; don’t delete it. GitHub provides the HTTPS certificate automatically (covering newberngrand.com and www).
  • Folders: the pages and scripts are in the top folder; pictures in images; database changes in supabase/migrations (numbered in order); server programs in supabase/functions.
  • Version number: bump-version.ps1 stamps every page with a new version (in version.json and on each script link) so browsers load the new files and open pages refresh themselves.

Publishing

.\bump-version.ps1
git add <the changed files>
git commit -m "What changed"
git push origin master

GitHub then runs pages build and deployment (see the repository’s Actions tab, or gh run list). When it shows a green check, usually within a minute, the change is live. Claude does all of this for you when you approve.

Never publish secrets. The repository is public. The only key in the website files is Supabase’s publishable key, which is meant to be public; the database rules protect the data. Private keys (Supabase service role, Resend API key) live only in Supabase’s secret settings.

6Supabase (database, logins, files)

Sign in at supabase.com/dashboard and open the marina project. Project ID afejychfqezorwyqfcsh; address https://afejychfqezorwyqfcsh.supabase.co.

What’s in it

  • Database (Table Editor / SQL Editor): members and slips, events and votes, ballots, documents, gallery photos and videos, gallery uploads waiting for review, announcements and who received them, help requests, minutes and reviews, Marina Chat messages (kept 90 days) and who is in the chat, Harbor Hunt games (hh_matches, hh_boards, hh_shots; the Poker Run uses the separate game_* tables), site settings, and the activity log. Row Level Security rules decide who can read or change each table.
  • Authentication: each slip logs in with its slip number and password. Behind the scenes the login is an account named slip-<slip>@members.newberngrand.com; these are not real mailboxes.
  • Storage: buckets marina-docs (private documents), gallery (public photos), gallery-videos (public approved videos) and gallery-pending (private uploads waiting for review).
  • Edge Functions (small server programs):
    • announce – sends Email Members announcements, tests and attachments
    • vote-email – vote receipts and the counting-committee notice
    • help-email – tells the office about a new help request
    • review – document review invitations and responses
    • request-password-reset – password reset emails
    • admin-members – admin tools for member logins (set a password, create a slip login)
  • Secrets (Edge Functions → Secrets): RESEND_API_KEY, MAIL_FROM (the sender name and address), RESET_FROM, SITE_URL. SUPABASE_URL and the service role key are provided automatically.
  • Realtime: Marina Chat uses Supabase Realtime, so new messages and game moves appear instantly. The chat_messages, hh_matches and hh_shots tables are in the supabase_realtime publication (Database → Publications); the same database rules decide who receives them.
  • Database extensions: pg_net lets the database call an Edge Function right after a vote or help request is saved.

How database changes are made

  1. Each change is written as a numbered file in supabase/migrations (for example 050_gallery_submissions.sql), so the repository is a complete record of how the database was built.
  2. Claude first runs it inside a trial transaction that is rolled back, testing it as a member, an admin and a visitor.
  3. After you say “make it live”, Claude applies it through the Supabase connector. The file is committed with the website change.

Settings to know: Authentication → URL Configuration should list https://newberngrand.com as the Site URL. If the domain ever changes, update it there and in the SITE_URL secret.

7Resend (email)

Sign in at resend.com. Resend sends mail on behalf of newberngrand.com; it doesn’t receive mail (replies go to the Reply-To address, for example the office or the member).

  • Domain: under Domains, newberngrand.com must show Verified. Verification depends on DNS records at DreamHost (see step 8): a DKIM record resend._domainkey and the send sub-domain records for bounces and SPF.
  • API key: under API Keys. The key is stored only as the Supabase secret RESEND_API_KEY. To replace it: create a new key in Resend (sending access), paste it into Supabase → Edge Functions → Secrets, check that a test email works, then delete the old key in Resend.
  • Sender: the From name and address come from the MAIL_FROM secret and must be an address at the verified domain.
  • Logs: Emails shows every message, whether it was delivered, bounced or marked as spam. Check here first when someone says they didn’t get an email.
  • Limits: each Resend plan has daily and monthly sending limits. If an announcement reaches the limit, Email Members pauses it and offers Resume later. Every member gets their own separate email; addresses are never copied to other members.

8DreamHost DNS (the domain name)

newberngrand.com uses DreamHost’s name servers (ns1.dreamhost.com, ns2.dreamhost.com, ns3.dreamhost.com). The DNS records are edited in the DreamHost panel: Websites → Manage Websites (or Domains), choose newberngrand.com, then DNS / custom records. The domain should be set to DNS only at DreamHost (not hosted there), because GitHub hosts the site.

Before changing DNS: take a screenshot of the current records. Changes can take from a few minutes to a few hours to reach everyone. Check with nslookup newberngrand.com or an online DNS checker. Never remove the MX, SPF or Resend records unless you mean to change email.

9Pointing other domain names to the site

GitHub Pages serves a site under one custom domain (newberngrand.com, plus its www). Other names the marina owns (for example a .net or a longer spelling) should forward visitors to https://newberngrand.com rather than being pointed at GitHub directly. If another domain’s A records point at GitHub’s addresses without being the Pages domain, visitors get a GitHub “404 Site not found” page.

If the other domain is at DreamHost

  1. In the DreamHost panel, add (or manage) the domain and choose Redirect.
  2. Redirect to https://newberngrand.com. Choose a permanent (301) redirect if offered.
  3. Turn on the free HTTPS certificate (Let’s Encrypt) for that domain so https:// links to it work too.
  4. Wait for it to take effect, then test both http:// and https://, with and without www.

If the other domain is registered somewhere else

  • Easiest: use that registrar’s own domain forwarding to https://newberngrand.com, or
  • change its name servers to ns1/ns2/ns3.dreamhost.com, add it to DreamHost and set up the redirect above. If the domain has email, copy its MX records over first.
  • You can also transfer the registration to DreamHost so everything is in one place.

If the main domain itself ever changes

  1. Put the new name in the CNAME file and in GitHub → Settings → Pages → Custom domain.
  2. Create the A and www records above for the new name, and turn the old one into a redirect.
  3. Update Supabase (Authentication → URL Configuration and the SITE_URL secret), verify the new domain in Resend, and ask Claude to update links to newberngrand.com in the pages and email functions.

10Making a change, start to finish

  1. Open Claude, Code tab, in the Marina1 folder. If others may have made changes, ask Claude to get the latest files first (git pull).
  2. Describe the change. Be specific about the page and the wording.
  3. Claude makes the edit and shows it in the built-in browser preview (the local server on port 8765), on a desktop and phone-sized screen.
  4. If the database or an Edge Function must change, Claude tests it without keeping anything and then asks.
  5. Say “make it live”. Claude applies database changes, runs bump-version.ps1, commits, pushes and waits for GitHub to finish.
  6. Check the live page. If something is wrong, tell Claude; every earlier version is kept on GitHub and can be restored.
  7. Update the Site Map (Help) when a page or feature is added, so the help stays accurate.

11Backups, security and good habits

  • Website files: GitHub keeps every version. Any change can be undone, and the whole site can be copied down again with gh repo clone.
  • Database: Supabase makes automatic backups (how long they are kept depends on the plan). Before big changes, ask Claude to export the important tables. The migration files rebuild the structure, but not the data.
  • Documents and photos live in Supabase Storage; download copies of anything irreplaceable.
  • Keys: never paste a private key (service role, Resend) into a page, a chat or an email. If one leaks, replace it at once (Supabase → Settings → API keys; Resend → API Keys).
  • People: keep at least two owners on GitHub, Supabase, Resend and DreamHost so the marina is never locked out. Remove access when someone leaves.
  • Renewals: keep the domain on auto-renew at DreamHost with a current payment card. An expired domain takes the website and the email down.

12Troubleshooting

ProblemWhere to look
A change isn’t showingGitHub → Actions: did pages build and deployment finish green? Was bump-version.ps1 run? Reload the page.
The site doesn’t open at allGitHub → Settings → Pages (custom domain still set, certificate OK); DreamHost DNS records; domain renewal.
“Not secure” warningGitHub → Settings → Pages → Enforce HTTPS. After DNS changes the certificate can take up to a day.
Someone can’t log inAdmin page → Members (is the slip active? set a new password). Supabase → Authentication → Users.
Emails not arrivingResend → Emails (delivered, bounced, spam?) and Domains (still verified?). Supabase → Edge Functions → the function → Logs.
An error on a pageTell Claude what you clicked and what you saw; it can open the page, read the browser console and the Supabase logs.
